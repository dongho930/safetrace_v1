# 연관 위협 사이트 발견 개편 명세

이 문서는 연관 후보 하위 조사를 **"연관 위협 사이트를 찾아 추가로 조사한다"** 는 목적에 맞게 고치는 구현 명세다. Claude Code 는 이 문서와 `CLAUDE.md` 작업 방식(브랜치 → 구현 → 측정 → 커밋 → Codex 검토 → PR, PR 을 쌓지 않음)을 따라 아래 PR 순서대로 진행한다. 앞 PR 이 머지된 뒤 다음 PR 을 main 에서 새로 딴다.

- 목적(사용자 결정, 2026-10-14): 하위 조사는 원래 URL 판단의 정확도를 올리는 수단이 아니다. **신고 1건에서 같은 조직이 운영하는 다른 위험 사이트를 찾아, 아직 차단되지 않은 곳을 추가로 조사**하는 기능이다.
- 유지하는 결정: 원 사건 안의 자동 하위 조사(2026-10-12 사용자 결정), 후보 최대 3곳·4단계·40초, 1단계만(하위의 하위 없음).
- 새 결정(사용자 결정, 2026-10-14): 원 사건 안의 빠른 하위 조사를 **1차 선별**로 쓰고, 선별 조건(§6b.2)을 모두 통과한 후보만 **자동으로 새 사건**을 만들어 전체 조사한다. 나머지 후보는 담당자 버튼으로 접수한다. 자동 사건은 조사 컨테이너를 늘려 병렬로 처리한다.
- 동결: 10/24. 시간이 모자라면 ① PR 5 의 '연관 묶음' 폴더·CSV → ② PR 4b(자동 생성) 순으로 뺀다. 사건 상세의 '연결된 사건'과 PR 4 버튼 접수는 남긴다.

## 1. 지킬 것 (모든 PR 공통)

1. **후보 주소·링크 글자는 공격자 값이다.** 지금처럼 `candidates.select` 가 스킴·포트·길이를 검사하고 쿼리·조각을 버린다. 링크 글자(앵커 텍스트)는 `mask_pii` 후 80자로 자르고, 화면에는 React 텍스트로만 출력한다.
2. **원래 사건의 판정은 하위 조사 결과로 바꾸지 않는다.** 연관 결과는 근거 카드·연관 목록·연결 정보로만 보여 준다.
3. **새 사건 만들기**: 연관 후보를 새 사건으로 만드는 길은 두 가지뿐이다. ① 조사관 이상 담당자의 버튼(PR 4, 사람 접수 한도 적용) ② 선별 조건을 통과한 후보의 자동 생성(PR 4b, 자동 전용 한도). 자동 생성은 **API 가** 원 사건의 종료 이벤트를 받을 때 한다. 격리망 안의 에이전트(워커)에는 사건을 만들 권한을 주지 않는다. 두 길 모두 같은 생성 함수를 쓰고 감사 로그를 남긴다.
4. **DB 스키마**: `Store` 는 `create_all` 만 쓰므로 **기존 `cases` 표에 열을 보태지 않는다**(기존 DB 에 반영되지 않음). 새 정보는 새 표로 둔다(새 표는 `create_all` 이 만든다).
5. **증거 체인**: 하위 조사 기록은 지금처럼 같은 체인에 `data.sub` 로 남긴다. 상태가 종료로 바뀔 때만 API 가 체인을 닫는다(지금 규칙 유지).
6. 관찰한 문구·도메인만 목록에 넣는다(`CLAUDE.md` 원칙). 지어낸 예시로 목록을 넓히지 않는다.
7. KISA 작성 기준(`tools/codex-review/prompt.md` 3.2·3.5·3.6)을 쓰기 전에 확인하고, 커밋 전에 대조한다. 특히 새 API 의 인가, 외부 입력 길이·개수 상한, CSV 수식 주입.

## 4. PR 2 — 링크 수집 범위 + 후보 순서 + 이미 차단됨

### 4.1 링크 수집 범위 넓히기

- 지금: `_note_links` 가 `obs.infos`(Jev 클릭 후보로 고른 요소)의 `href` 만 모은다.
- 바꿈: 관찰할 때 **화면의 모든 `a[href]`** 에서 `http`·`https` 절대 주소를 따로 모은다(Jev 에 보내는 클릭 후보와 별개).
  - `observe.py` 에 링크 수집 스크립트를 따로 두거나 `COLLECT_JS` 결과에 `links: [{href, text}]` 를 보탠다. 페이지당 최대 200개, `href` 2048자, `text` 80자. 보이지 않는 링크도 모으되 `visible: bool` 을 함께 둔다.
  - 사건 전체 누적 상한 지금 그대로 100(`_note_links` 의 `len(seen) < 100`). 앵커 글자는 `mask_pii` 후 저장한다.
  - **Jev 에 보내는 상태(`PageState`)는 바꾸지 않는다** → 원래 사건의 탐색·판단은 그대로여야 한다(§4.4 확인).
- 관찰 기록(`observe`)에 링크 목록 전체를 넣지 않는다(체인이 커진다). 대신 탐색 종료 시 `candidates` 기록의 `found` 가 근거가 된다. 링크 수만 `observe.data.links_seen` 으로 남긴다.

### 4.2 후보 고르는 순서

`candidates.select` 를 점수 순으로 바꾼다(동점이면 지금 순서).

| 점수 | 조건 |
|---|---|
| 3 | 경유 도메인(`via`) — 지금처럼 맨 앞 |
| 2 | 앵커 글자나 주소에 위협 단서가 있는 링크. 단서 단어는 **이미 코드에 있는 것만** 쓴다: `decision/providers.py` 의 `_THREAT_SIGNS` 와 단축 서비스 대기·경고 문구. 새 단어를 지어내지 않는다 |
| 1 | 조사한 사이트의 이름과 뚜렷한 조각을 나눠 갖는 도메인(예: 원래 사이트가 `kc-telegram.xxx` 면 `kc-…`). 조각은 하이픈·점으로 나눠 4글자 이상, 흔한 단어(`www`, `m`, `app`, `shop`, `online` 등 관찰한 것만)는 뺀다 |
| 0 | 나머지 |
| 제외 | **흔한 대형 사이트**: 지금 로컬 DB 사건과 `var/eval` 기록에서 후보로 나왔고 하위 조사 결과가 정상이었던 대형 서비스 도메인(구글·유튜브·앱 마켓·SNS 등)을 뽑아 목록으로 만든다. **실제로 관찰한 것만** 넣고, 목록과 출처(어느 기록에서 봤는지)를 PR 설명에 적는다 |

- `MAX_FOUND`(기록 20)는 그대로. 기록 20개도 점수 순으로 채운다(점수 0 은 뒤로).
- 후보 항목에 `score`(0~3)와 `text`(앵커 글자, 80자)를 보탠다. API `_clean_candidates` 의 허용 항목에 `score`(0~3 정수), `text`(80자), `blocked`(bool)를 보탠다.

### 4.3 이미 차단됨 표시

- `_investigate_candidates` 결과에 `blocked: r.network_filtered` 를 싣는다(warning.or.kr 화면·이름 기준 연결 리셋, 원래 조사의 #21 감지와 같은 값).
- 콘솔 연관 목록·경로 지도 가지·근거 카드의 후보 표시에 "이미 차단됨"을 붙인다. 근거 카드 ⑤(연관 사이트도 의심)는 **차단되지 않은 위협 후보를 먼저** 고른다.

### 4.4 확인

- 시험: 링크 200개·긴 주소·`javascript:`·내부 주소·개인정보가 든 앵커 글자가 있는 시험 페이지로 수집 상한·정리를 고정한다(`tests/test_candidates.py` 확장). 흔한 대형 사이트가 제외되고 단서 링크가 앞에 오는지.
- 측정: 55개 목록 3회 + 오늘의 실사이트 세트 3회.
  - **원래 판정 정답률이 PR 1 기준선과 같아야 한다**(시험·정상·KISA 각 그룹, 놓침·오탐 수). 다르면 Jev 입력이 바뀌었는지부터 본다.
  - 발견 지표 전/후(위협 발견 비율, 발견 사이트 수, 아직 안 막힌 비율, 후보 1곳당 시간).

## 5. PR 3 — 원래 결과 먼저

### 5.1 흐름

```
원래 조사 → Safe Browsing → 담당자 검토 전환 판단 → [원래 결과 이벤트] → 연관 후보 하위 조사 → [종료 상태 이벤트]
```

- `runner._investigate`: 담당자 검토 전환(escalation)까지 정한 뒤, 하위 조사를 시작하기 **전에** 상태 이벤트를 하나 더 보낸다.
  ```json
  {"type": "status", "status": "RUNNING", "phase": "related",
   "main": {"status": "<최종이 될 상태>", "reason": "<사유>"},
   "threat": {...}, "final_url": "...", "safebrowsing": {...},
   "candidates": [/* 후보 목록, 하위 조사 결과 없음 */]}
  ```
  - `RUNNING → RUNNING` 은 지금 `store` 에서 허용된다. `add_event` 가 `threat`·`final_url`·`safebrowsing`·`candidates` 를 사건에 반영한다(지금 코드 그대로).
  - 하위 조사를 하지 않는 사건(`followup` 거짓)은 지금처럼 종료 상태 하나만 보낸다.
- 종료 상태 이벤트는 지금과 같다(원래 사건의 `status`·`reason`·`threat` 는 원래 결과 이벤트와 같아야 한다 — 시험으로 고정).
- **상태 값은 늘리지 않는다**(`TERMINAL`, `_NEXT_STATUS`, 접수 한도의 `PENDING` 그대로).

### 5.2 사건에 '원래 결과 나옴' 표시

- `cases` 표에 열을 보탤 수 없으므로(§1-4) 새 표 `case_phase`(case_id PK, phase, main_status, main_reason, at)를 둔다. `record_event` 가 `phase: "related"` 상태 이벤트를 받으면 한 줄 쓴다. 이 이벤트는 **`RUNNING` 이고 `threat` 가 있을 때만** 받아들인다.
  - **구현(Codex 지적 반영)**: 표 이름은 `case_main_result`(증거 끝 열을 더해 첫 판 `case_phase` 와 열이 달라짐). 원래 결과 이벤트는 **한 번만** 받고, 워커가 보낸 원래 조사의 마지막 기록 번호를 API 가 체인 앞부분의 서명까지 검증한 끝(`main_head_seq`·`main_head_hash`)을 함께 둔다. 그 뒤 상태 이벤트는 연관 후보 결과만 반영하고 종료 상태는 원래 결과로 맞춘다. §5.3 의 판정 증거 끝은 서명 서비스의 최신 head 가 아니라 이 원래 조사의 끝이다.
- `CaseOut` 에 `phase`(`"related"` | null)와 `main_status`(원래 결과 상태)를 보탠다. 목록·상세 모두.

### 5.3 판정 가능 시점

- `verdicts.save`: `RUNNING` 이어도 **`case_phase.phase == "related"` 이면 판정을 받는다.** 나머지 `RUNNING`·`QUEUED` 는 지금처럼 거절.
- 판정에 묶는 증거 끝(head): 체인이 아직 열려 있으므로 닫지 않고 서명 서비스의 `head` 조회(`ChainAdmin.head`, 개발 모드는 같은 프로세스의 체인 끝)를 쓴다. 판정 화면 문구는 지금처럼 "증거 EV-n까지 확인".
- 검토 패키지·보고서 내보내기는 지금처럼 **종료 상태(체인 닫힘)에서만** 허용한다. 콘솔은 "연관 사이트 조사가 끝나면 내려받을 수 있습니다"로 안내한다.
- 시험(`tests/test_verdicts.py` 확장): 원래 결과 전 `RUNNING` 은 거절, 원래 결과 뒤는 허용·head 가 그 시점 값, 종료 뒤 판정 기록이 유지, 자동화 토큰은 여전히 403.

### 5.4 콘솔

- 목록·폴더: `phase === "related"` 사건은 `main_status` 기준 폴더(검토 필요·위협 의심 등)에 들어가고, 상태 칩 옆에 "연관 사이트 조사 중"을 붙인다. 조사 중 폴더 숫자에는 넣지 않는다.

## 6b. PR 4b — 선별 조건을 통과한 후보 자동 사건 생성 + 병렬 조사

### 6b.1 흐름

```
원 사건: 원래 조사 → [원래 결과] → 빠른 하위 조사(최대 3곳, 4단계·40초) → [종료]
                                                                      │ API 가 종료 이벤트를 받음
                                                                      ▼
                                              선별 조건(§6b.2) 검사 → 통과한 후보만 새 사건(source=related, auto)
                                                                      ▼
                                              st:jobs → 비어 있는 조사 컨테이너가 전체 예산으로 조사
```

- 빠른 하위 조사는 그대로 둔다(1차 선별, 원 사건 근거). 자동 사건은 전체 예산으로 다시 조사해 사이트마다 자기 체인·판정·검토 패키지를 갖는다.

### 6b.2 선별 조건 (전부 만족해야 자동 생성)

순수 함수 `safetrace/related.py` 의 `auto_targets(parent, candidates, settings) -> list[(candidate, reason)]` 로 둔다. 평가 도구가 같은 함수를 쓴다(§6b.6).

| # | 조건 | 이유 |
|---|---|---|
| 1 | 설정 `related_auto` 가 켜져 있음 | 바로 끌 수 있게 |
| 2 | 부모 사건이 연관 사건이 아님(`source != "related"`) | 깊이 1. 자동·버튼 자식 모두 다시 자동 생성하지 않는다 |
| 3 | 후보가 하위 조사됨(`sub` 있음), 하위 조사 상태가 `UNREACHABLE`·`BLOCKED`·`FAILED` 아님 | 선별 결과가 있는 것만 |

- 단축 서비스·공용 호스팅 목록은 `related.py` 에 상수로 두고, **평가·신고 자료에서 실제로 본 것만** 넣는다(지금 저장소에 있는 것: bit.ly, tinyurl.com, han.gl, lrl.kr, goo.su, c11.kr, xzx.kr, muz.so, 5du.pl, tny.kr, iii.im, go9.co, t.ly / 공용 호스팅 pages.dev, dothome, creatorlink). 출처를 주석에 적는다. PR 5 가 이 목록을 그대로 쓴다.
- 통과하지 못한 후보는 지금처럼 PR 4 버튼으로 접수할 수 있다. 콘솔에는 못 만든 이유를 짧게 보여 준다(§6b.5).

### 6b.3 API

- `record_event` 가 원 사건의 **종료 상태**를 처리(체인 닫기·`add_event`)한 **뒤에** `auto_targets` 를 부르고, 통과한 후보마다 PR 4 의 `create_related_case(..., actor="system:related", auto=True)` 를 부른다.
  - **구현(Codex 지적 반영)**: 후보는 종료 이벤트의 목록(워커가 보고한 값)이 아니라 닫고 검증한 체인의 원래 조사 후보 기록(`candidates`)과 하위 조사 결과 기록(`candidate_results`)을 합쳐 고른다(`_signed_candidates`, 검증 실패면 만들지 않음). 조건 3 의 상태는 완료·검토 필요일 때만(상태가 없으면 아님).
  - 검사와 생성은 `create_case` 의 `_intake_lock` 안에서 한다(동시에 끝난 두 사건이 같은 호스트로 두 사건을 만들지 않게).
  - 종료 이벤트가 다시 배달돼도(`xautoclaim`) `(parent_id, candidate_url)` 유일 제약과 사전 조회로 한 번만 만든다.
  - 자동 생성이 실패해도 원 사건 처리와 이벤트 소비는 멈추지 않는다(예외를 잡아 로그·감사 `case.create_related_auto_failed` 후 계속).
  - 감사 로그 `case.create_related_auto`(부모 id, 후보 주소 앞 200자, 도착 호스트, 위협 유형·확률).
- **사람 접수 한도와 분리**: `_check_intake_limits` 의 전체 한도(200) 계산에서 `created_by == "system:related"` 사건을 뺀다. 자동 사건은 조건 9 의 전용 한도만 받는다. 담당자가 버튼으로 만든 연관 사건은 지금처럼 그 담당자의 한도에 들어간다.
- 상세 `children` 항목에 `auto` 를 보탠다. 원 사건 상세에 `auto_skipped: [{url, reason}]` 를 보탠다(자동 사건이 없는 하위 조사 후보와 이유 코드). 새 표를 두지 않고 읽을 때 계산한다:
  - 시점과 무관한 조건 1~6·10 은 다시 계산해 `disabled|not_threat|shortener|brand_site` 로 준다(`blocked` 는 조건 5 를 빼면서 없어짐).
  - 1~6 을 통과했는데 자식이 없으면 `limit_or_duplicate`(조건 7~9, 그때의 한도·중복은 감사 로그 `case.create_related_auto_skipped` 에 남긴다).

  ```python
  related_auto: bool = True
  related_auto_per_case: int = Field(3, ge=0, le=3)
  related_auto_max_pending: int = Field(10, ge=0, le=50)
  related_auto_dedup_days: int = Field(7, ge=1, le=30)
  ```

### 6b.4 병렬 조사 (조사 컨테이너 늘리기)

지금 코드에서 확인한 것: 워커는 `XREADGROUP count=1` 로 한 번에 1건만 처리하고(`agent/worker.py`), 컨슈머 이름이 `socket.gethostname()` 이라 컨테이너마다 다르다. `docker-compose.yml` 의 `agent` 에는 `container_name`·호스트 포트가 없다. 끊긴 작업 회수(`recover_interrupted`)의 `min_idle_ms` 가 최대 조사 시간보다 길어 살아 있는 다른 워커의 작업을 가로채지 않는다. → **코드 변경 없이 `--scale agent=N` 으로 늘릴 수 있을 것으로 보인다. 실제로 확인한다.**

- 확인할 것:
  1. `docker compose --profile demo up -d --scale agent=2` 로 두 컨테이너가 각자 다른 사건을 가져가는지(같은 사건을 두 번 조사하지 않는지).
  2. 실시간 화면(`RedisLivePublisher`)·녹화·증거 폴더가 두 컨테이너에서 섞이지 않는지(사건 id 별 경로인지).
  3. 한 컨테이너를 조사 중에 죽였을 때 `recover_interrupted` 가 다른 컨테이너에서 그 사건을 FAILED 로 마무리하는지.
  4. 메모리·CPU: 컨테이너당 제한 2 CPU·2GB. 시연 장비의 코어·메모리로 2개가 시간 초과 없이 도는지(CLAUDE.md: 평가 중 콘솔 사건을 넣으면 CPU 를 나눠 써서 시간 초과가 났다).
- 기본값은 지금처럼 1개로 두고, README 에 늘리는 방법과 장비 조건을 적는다. 시연은 2개로 한다(장비가 버티면).
- 평가 도구는 `docker compose exec -T agent` 로 컨테이너 안에서 `investigate` 를 직접 부른다(API·대기열을 거치지 않으므로 자동 생성은 평가 정답률에 영향이 없다). 늘린 상태에서는 1번 컨테이너만 쓰게 되지만, **평가 중에는 1개로 줄인다**(같은 호스트 CPU 를 나눠 써 숫자가 흔들린다).
- 사람 신고 우선 대기열(별도 스트림)은 이번에 만들지 않는다. 자동 사건 전용 한도(10)와 컨테이너 수로 대기 시간을 막는다. 실제 스택에서 "자동 사건 3건이 대기 중일 때 들어온 사람 신고가 조사를 시작하기까지 걸린 시간"을 잰다.

### 6b.5 콘솔

- 원 사건 연관 목록의 후보마다:
  - 자동으로 만든 사건이 있으면 "자동 접수됨 · 사건 보기 · {상태}".
  - 자동으로 못 만든 하위 조사 후보는 이유 한마디(자동 접수 꺼짐 / 정상으로 봄 / 이미 차단됨 / 단축 주소 / 자동 한도·중복) + [새 사건으로 접수] 버튼(PR 4).
- 목록 행: 자동 사건은 "연관·자동" 배지, 버튼 사건은 "연관" 배지. 상단 분류 폴더 숫자는 지금 규칙 그대로(상태 기준)이고, 목록 필터에 출처(신고·KISA·연관)를 둔다 — 사람이 넣은 신고 건수와 섞어 세지 않게.
- 자식 사건 상세 위쪽: "연관 사이트 · {부모 신고 URL} 사건에서 자동 발견" 링크.
- 실시간 화면은 조사 중 사건이 여럿일 수 있다. 지금처럼 하나를 보여 주되, 사람 신고를 자동 사건보다 먼저 고른다.

## 7. PR 5 — 사건 간 연결

### 7.1 데이터

- 새 표 `case_sites`: `id`, `case_id`(index), `host`(253, index), `site`(253, index, `candidates.site_of`), `role`(`start`|`final`|`via`|`link`|`candidate_final`), `threat`(32, null), `blocked`(bool), `generic`(bool), `created_at`.
- 채우는 때: `record_event` 가 **종료 상태**를 받았을 때 사건의 `url`·`final_url`·`candidates`(+ 하위 조사 `final_url`)에서 호스트를 뽑아 한 번에 쓴다(사건당 최대 30줄).
- `generic`: 여러 사건을 잘못 이어 붙이는 공용 호스트. 이 표시가 있으면 **사이트(등록 도메인) 기준으로 묶지 않고 호스트가 정확히 같을 때만** 잇는다.
  - 단축 서비스 호스트는 **아예 잇지 않는다**(같은 단축 서비스를 썼다고 같은 조직이 아니다).
  - 공용 호스팅은 호스트 일치만.
  - 목록은 PR 4b 가 `related.py` 에 둔 상수(관찰한 것만, 출처 주석)를 그대로 쓴다.
- 기존 사건 채우기: `python -m safetrace.related backfill` (종료된 사건 전부, 여러 번 돌려도 같은 결과).

### 7.2 API

- `GET /api/cases/{id}/links` (열람자 이상): `{parent, children, shared: [{site, hosts, roles, cases: [{id, url, status, threat, verdict}]}]}`. 최대 50건. 자기 자신 제외.
- `GET /api/related-groups?min=2&limit=50` (열람자 이상): 최근 종료 사건 500건 범위에서 `generic` 아닌 사이트로 사건을 이어(합집합 찾기) 사건이 `min` 개 이상인 묶음. 묶음마다 사이트 목록(위협·차단 여부)과 사건 목록(상태·판정). 계산 상한(사건 500·사이트 5,000)을 넘으면 잘라서 `truncated: true`.
- `GET /api/related-groups/{group_key}.csv` (조사관 이상): 묶음의 사이트·사건 표. 감사 로그 `related.export`. **CSV 수식 주입 방지**: 값이 `=`, `+`, `-`, `@`, 탭, CR 로 시작하면 앞에 `'` 를 붙인다. 파일명은 고정 형식(`safetrace-related-<날짜>-<번호>.csv`).

### 7.3 콘솔

- 상세의 조사 경과 탭에 **"연결된 사건"** 탭: 부모·자식 사건, 같은 사이트가 나온 다른 사건(사이트별로 묶음). 각 사건으로 이동.
- 분류 폴더에 **"연관 묶음"**: 묶음 목록(사건 수·위협 사이트 수·아직 안 막힌 수) → 묶음을 고르면 사이트·사건 표 + [CSV 내려받기](조사관 이상) + 아직 안 막힌 사이트마다 [새 사건으로 접수](PR 4 재사용).
  - **구현(Codex 지적 반영)**: '아직 안 막힌 수' 대신 '회선 차단 추정' 수를 따로 센다. 회선 차단 감지는 조사 대상 서버가 흉내 낼 수 있는 추정이라, 위협 집계에서 빼거나 접수 버튼을 숨기지 않는다.

### 7.4 확인

- 시험: 단축 서비스만 같은 두 사건은 잇지 않음, 공용 호스팅은 호스트가 같을 때만, 같은 도박 사이트를 후보로 가진 두 사건은 이음, CSV 수식 주입 이스케이프, 권한(열람자는 CSV 403).
- 실제 스택: 평가 결과로 쌓인 사건(또는 backfill 한 로컬 DB)에서 묶음 수와 계산 시간.
