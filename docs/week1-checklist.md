## 5. 점검 중 찾아 고친 것

- **검토 패키지가 체인의 파일명을 검사하지 않음.** 증거 체인은 조사 대상 페이지를 다루는 에이전트 컨테이너가 쓰고, API 는 읽기 전용으로 마운트한다. 파일을 내려주는 기존 API 는 파일명을 허용 목록으로 검사했지만, #35 의 패키지·ZIP 은 체인에 적힌 이름을 그대로 써서 에이전트가 뚫려 `../../` 이름을 넣으면 증거 폴더 밖 파일을 ZIP 에 담을 수 있었다. 이제 허용 목록에 맞고 `files/` 안으로 풀리는 파일만 담고, 이상한 이름은 검증 실패로 드러난다. 수정 전 코드에서 새 시험이 실패(`../../secret.txt` 포함)하고 수정 뒤 통과함을 확인했다(`test_unsafe_file_names_from_chain_are_not_exported`).
- **문서와 실제 배치가 다름.** `evidence.py` 설명은 서명 키가 "에이전트 컨테이너에는 없음"이라 했지만 실제로는 에이전트가 서명하므로 키를 가진다. 설명을 고치고, 위협 모델에 그 위험과 남은 과제를 적었다(아래 6절).
- 위협 모델에 1주차 위협(판정 덮어쓰기·동시 저장, 판정·내보내기 부인, AI·자동화 토큰의 판정 확정, 패키지 경로 조작·반출)과 대응 시험을 추가했다.

## 6. 아직 하지 않은 것 (정직한 현황)

- **서명 키가 에이전트(워커)에 있다.** 워커가 뚫리면 그 뒤 기록은 위조 서명될 수 있다. 이미 끝난 사건은 DB 의 head 와 내보낸 패키지로 대조할 수 있다. 서명을 별도 서비스로 분리하는 일은 남은 과제다.
- 로그인 제한은 계정별 잠금뿐이다. 여러 계정에 같은 비밀번호를 돌려 보는 공격(IP 기준 제한)은 막지 않는다. 운영 배포 전 리버스 프록시에서 IP 제한을 둘 것.
- 감사 로그는 일반 DB 테이블이다(해시 체인 아님). DB 관리자는 고칠 수 있다.
- `package.sig` 는 HMAC 이라 서명 확인은 SafeTrace 서버에서만 된다. 받은 쪽은 SHA256SUMS·해시 체인으로 내용이 바뀌지 않았는지만 확인할 수 있다(공개키 서명은 하지 않음).
- ZIP 은 메모리에서 만든다. 지금 가장 큰 사건 증거가 약 17MB 라 요청 하나에 수십 MB 를 쓴다. 내려받기는 조사관 이상만 가능해 동시 요청이 많지 않다고 보고 그대로 두었다.
- 같은 검토관이 판을 연속으로 바꿀 수 있다(두 사람 확인 규칙 없음). 기획서 요구는 아니다.
- `docs/prep-checklist.md` 6절의 "판정 저장·계정은 1주차 범위" 문장은 10/4 시점 기록이라 그대로 둔다.
